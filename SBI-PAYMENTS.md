# SBI ePay checkout and double verification

Event creators choose Free Event or Paid Event in the event wizard. Both event types support custom registration fields and collect attendee name and email. Paid registrations require a positive ticket price and continue through SBI ePay; free registrations have no fee/payment fields, complete immediately in the attendee roster, and never create an SBI order. Manual QR submissions are rejected.

New public signups are attendees. Only a Super Admin can grant the ORGANIZER role or create an event-admin account; accounts created through event sharing remain attendees and receive only the explicitly shared event access.

Before calling Order Create, the backend saves a unique `merchantOrderNumber`, the frozen amount, and `orderStatus = CREATED`. The callback URL is `${BACKEND_URL}/api/bookings/sbiepay/callback`; configure BACKEND_URL as the externally reachable backend origin for SBI callbacks. URL-encoded POST callbacks and GET callbacks are supported. The decoded callback identifies the booking, triggers Order Search, and redirects to its private status link. Callback payment claims never directly grant registration.

`SbiepayVerificationJob` runs every minute while the backend is running. It pages through all pending SBI bookings that have a merchant reference, including CREATED, ATTEMPTED and unknown states. For each it calls `sbiePayClient.order.search` with `orderAmount`, `orderRefNumber`, and the optional stored `sbiOrderRefNumber` and `atrnNumber`. Failures are isolated per order and retried on the next run. API requests time out after 30 seconds. A process skips overlapping job runs; serializable transactions prevent concurrent callbacks or backend instances from double-counting seats or issuing duplicate confirmation emails during verification.

The observed sandbox SDK response is `data: [[{ orderInfo, paymentInfo: [...] }]]`: orderStatus and merchant reference are in orderInfo, while amount and ATRN are in paymentInfo. Flat responses are also supported. Order Search responses must match the stored merchant reference and amount. Only `orderStatus` decides payment completion. The current explicit mapping is PAID/SUCCESS to paid and FAIL/FAILED to failed (case-insensitive). CREATED, ATTEMPTED and all other values stay pending. Confirm these terminal strings against the merchant's SBI response documentation before production; do not infer success from an HTTP/API status, transactionStatus, a redirect, or missing data. Successful orders confirm registration and send a ticket once. If capacity has been exhausted, payment is recorded as received, but registration remains pending for organizer resolution and no ticket is issued. SBI orders cannot be changed using manual payment review routes.

The migration `20261007000000_sbiepay_order_verification` adds the references and last-check timestamp. The migration `20261022000000_add_event_type` adds the explicit event type and derives it for existing events from their saved price. Legacy SBI bookings created by the previous implementation have no stored merchant order reference, so the job cannot recover their payment state automatically. Backfill their actual merchant references from merchant records; never invent references or submit new payments to reconcile old orders. Existing historical QR records are retained.

`SBIEPAY_ENVIRONMENT` selects SANDBOX or LIVE. Gateway credentials stay in the backend environment. A reachable backend must be running for cron verification. The browser status link refreshes every 10 seconds; confirmation email requires configured mail delivery.

Validation: `npm run build` and `node --test test/sbiepay-payments.test.cjs test/sharing-permissions.test.cjs`. Tests use mocked SBI responses; they do not make live payment requests.
